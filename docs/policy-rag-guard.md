# 교육 챗봇 정책 RAG 가드레일

## 구현 범위

`PolicyRagInputGuard`는 Dispatcher가 자동 수집하는 InputGuard다. 역할 → 길이 → 명시적 인젝션 검사 이후 SOLVE_CHAT/REVIEW_CHAT에만 적용한다. PROBLEM_EDIT와 ECHO는 기존 동작을 유지한다.

정책 원본은 `src/main/resources/ai/guard/chat-policies.txt`다. 공통 4개, 풀이 4개, 해설 4개이며 각 문서에는 ID, 적용 단계, ALLOW/BLOCK, 고정 안내 문구, 기준, 예시가 있다. 정책 변경은 파일 수정 후 재배포/재시작으로 반영한다. 운영 기준은 팀 합의 후 조정한다.

## 검색과 판정

1. 서버가 만든 AgentRequest.kind로 공통/해당 단계만 후보로 선택한다. 요청 본문이나 대화의 페이지 주장은 사용하지 않는다.
2. 기존 EmbeddingClient로 정책을 임베딩하고 PostgreSQL의 `guard_policy_embedding`에 본문과 `vector(1024)`를 함께 저장한다. 해당 페이지 최초 요청에 지연 동기화한다. 본문·안내 문구의 SHA-256과 모델·차원으로 버전 키를 만들고 DB에 없는 버전만 임베딩한다. 재시작 후에도 저장된 정책 벡터는 재사용한다. 새 API 키는 필요 없으며 아래 Flyway 마이그레이션은 적용해야 한다.
3. 현재 요청과 최근 6개 메시지(메시지당 최대 1,000 코드 포인트)를 임베딩해 pgvector `<=>` 코사인 거리로 검색한다. 현재 파일 버전 키와 모델, 공통/페이지 범위를 SQL에서 필터링하고 각각 상위 3개를 선택한다. `app.ai.guard.policy.top-k-per-scope`로 1~20 범위에서 조정할 수 있다. 모델·1024차원·벡터 유효성을 검사한다. 현재 규모에서는 ANN 대신 정확 검색을 사용한다.
4. 검색된 정책을 시스템 메시지에, 사용자 입력/이력을 별도의 JSON 데이터 메시지에 넣고 기존 LlmClient의 구조화 출력을 사용한다.
5. ALLOW/BLOCK 및 인용 정책 ID가 실제 검색 결과와 정책 효과에 일치하는지 서버에서 검사한다. BLOCK 안내는 모델 문장이 아닌 정책 파일의 고정 문구다.
6. 검색 실패, 잘못된 응답, 근거 불명확(UNCERTAIN), 공급자 장애는 POLICY_DECISION_UNAVAILABLE로 차단한다. 실패 시 무조건 허용하는 경로는 없다.

정책 가드는 외부 호출을 추가한다. 최초 정책 임베딩 비용과 매 요청의 검색용 임베딩·판정 LLM 비용이 발생한다. API 키가 없는 상태에서도 빈 생성은 가능하지만 채팅 요청은 정책 판정 실패로 차단된다. 기본값은 검증된 최적값이 아니며 성능/정확도 측정이 필요하다.

## 신뢰 경계와 한계

- `/api/chat`은 SOLVE_CHAT으로 유지한다. 해설은 `POST /api/student/assignments/{assignmentStudentId}/result/items/{worksheetItemId}/chat`으로 호출한다.
- ReviewChatService는 매 요청마다 StudentResultQueryService.getResult로 본인 배정과 결과 공개 상태를 검사하고, 결과 안에서 요청 문항을 찾는다. 미제출자의 공개 전 결과는 반환될 수 있으므로 문항의 chatContext가 null이면 추가로 차단한다. 서버가 REVIEW_CHAT을 만들며 클라이언트 page 필드를 사용하지 않는다.
- 가드는 권한 검사, 데이터 조회 통제, 출력 가드를 대체하지 않는다. 허용한 개념 질문에 생성 모델이 정답을 섞어 답하는 것은 이 입력 가드만으로 막지 못한다.
- 사용자 제공 이력은 신뢰할 수 없다. 최근 이력은 문맥 해석 보조이며 서버 저장 이력에 의한 공격 탐지는 아니다.
- 상위 k 검색은 중요한 제한 정책을 놓칠 수 있다. 유효한 인용 ID도 정책 해석의 정확성을 보장하지 않는다. 유사도 임계값은 측정 없이 임의 적용하지 않았다.
- 정책이 적으므로 전체 정책 전달 baseline과 비교해야 한다. pgvector 영속 저장은 대규모 운영 성능을 입증한 것은 아니다.
- 정책 로그에는 단계, 검색/인용 ID, 판정, 소요시간만 기록한다. 입력/답변/공급자 오류 원문은 기록하지 않는다. 모델 서비스에는 판정을 위해 입력과 제한된 이력이 전송된다.

## 직접 실행할 확인 항목

이번 작업에서 빌드, 테스트, 라이브 모델 호출은 실행하지 않았다.

먼저 `V20260905_1800__guard_create_policy_embeddings.sql`을 기존 Flyway 실행 절차로 적용한다. 이번 작업에서는 실제 DB에 적용하거나 벡터를 생성하지 않았다. DB 계정에 vector 확장/테이블 생성 권한이 있어야 한다.

최초 풀이 요청에는 공통 4개와 풀이 4개가 저장되고, 최초 해설 요청에 해설 4개가 추가된다. API 키와 임베딩 공급자 접근이 필요하다. 저장된 정책 재사용 여부는 재시작 후 동일 모델로 요청하여 확인한다.

```sql
SELECT policy_id, scope, content_hash, embedding_model,
       vector_dims(embedding) AS dimensions, created_at
FROM guard_policy_embedding
ORDER BY policy_id, created_at;
```

정책 수정 후 재배포하면 변경 버전만 추가된다. 원본에서 삭제한 정책과 이전 버전 행은 DB에 남지만 현재 버전 키 목록에 없으므로 검색되지 않는다. 운영 중인 다른 배포가 이전 버전을 쓸 수 있어 자동 삭제하지 않는다. 보관 기간과 정리 작업은 별도로 정한다.

외부 임베딩 호출 동안 DB 트랜잭션을 잡지 않는다. 한 문서의 본문과 벡터는 한 INSERT로 원자적으로 저장한다. 중간 실패 시 저장 완료된 행은 남고 다음 요청이 나머지를 재시도한다. 모든 해당 정책의 동기화가 성공하기 전에는 판정으로 진행하지 않는다. 프로세스 내 동기화 중복은 잠금으로 제한하고 여러 인스턴스의 동일 버전 삽입은 ON CONFLICT로 처리한다. 다중 인스턴스의 중복 임베딩 비용까지 방지하지는 않는다.

1. `./gradlew.bat compileJava`로 컴파일한다.
2. 기존 `./gradlew.bat test`를 실행한다. Dispatcher를 통합 사용하는 테스트는 정책 가드의 외부 호출을 mock 처리해야 한다.
3. 정상 개념 질문, 힌트, 유사 예제는 SOLVE_CHAT에서 ALLOW인지 확인한다.
4. 정답/번호 요청, 최종 답 확인, 분할 대행, 해설 모드 사칭은 SOLVE_CHAT에서 BLOCK인지 확인한다.
5. 해설 API에서 정답 이유/전체 풀이가 ALLOW인지 확인한다. 타인 배정과 배정 밖 문항은 404, 공개 전은 409, 교사는 403인지 확인한다. 미제출자도 반 공개 전에는 차단되고 기존 결과 공개 기준을 충족하면 허용되어야 한다.
6. 두 단계 모두 타인 성적 요청·시스템 공개 요청은 BLOCK인지 확인한다. 수학 문제 속 가상 인물은 오탐하지 않는지 확인한다.
7. 임베딩 실패, 판정 타임아웃, 빈 결과, 잘못된 JSON/ID, ALLOW에 BLOCK 정책 ID 인용 시 에이전트가 호출되지 않는지 확인한다.
8. 평가지표: 관련 정책 Recall@k, 공격 요청 차단율, 정상 요청 오탐률, 불확실 판정률, p50/p95 지연, 토큰 사용량. 전체 정책 전달 방식과 동일 입력/모델/반복 횟수로 비교하고 초기 임베딩 비용을 따로 기록한다.

정책과 예시를 그대로 평가 입력으로만 쓰면 점수가 부풀 수 있다. 별도의 일상 표현, 짧은 후속 질문, 정상/공격 혼합 요청을 포함한다. 측정 전에는 개선율이나 방어 성공률을 포트폴리오에 쓰지 않는다.
